2. It doesn't free memory back to the OS immediately when tensors are deallocated. Instead, it holds onto it in a cache pool.
3. Why? To avoid the overhead of frequent malloc/free calls to the GPU driver, which is slow and causes synchronization stalls.
4. Fragmentation occurs because:
   - Training involves dynamic shapes (different batch sizes, variable sequence lengths, etc.).
   - Tensors are allocated and freed in varying sizes over time.
   - The allocator breaks memory into chunks. As large tensors are replaced by smaller ones with different alignment/sizes, the free space becomes scattered ("free but unusable").
   - The caching allocator uses a "suballocator" that manages these chunks. If you request 10MB, it grabs 10MB from the cache or grows the pool. When freed, those 10MB are back in cache. But if another op needs exactly that block vs. two adjacent free blocks of slightly different sizes, fragmentation limits what can be reused without requesting more from the driver.
   - `torch.cuda.memory_allocated()` vs `torch.cuda.memory_reserved()` illustrates this gap (the "wasted" space due to fragmentation/caching).

Let's draft a clear, structured explanation.

Here is how PyTorch manages GPU memory and why you often see it fill up faster than your actual tensors should require.

1. The Caching Allocator

PyTorch does not call the CUDA driver (cudaMalloc/cudaFree) every time you create or delete a tensor. Instead, it uses a caching allocator in CPU Python space that interacts with a device-side suballocator on the GPU.

When a tensor is freed: 1. The memory is not returned to the system immediately. 2. It is kept in a “cache pool” inside PyTorch. 3. Future allocations are satisfied from this cache first.

Why do this? Talking to the CUDA driver involves expensive kernel-to-driver transitions and implicit GPU synchronization. By caching freed memory, PyTorch drastically reduces cudaMalloc/cudaFree overhead, which is essential for high-throughput training loops.

2. Why Fragmentation Happens

Fragmentation occurs because the cache holds onto blocks of varying sizes that don’t always fit neatly together. Training workflows make this worse for three reasons:

  • Dynamic Shapes: Modern models use variable-length sequences (e.g., NLP with padding/masking) and mixed-precision or dynamic batch sizes. A layer might need a 12MB buffer in step t, but only a 4MB buffer in step t+1. The remaining 8MB sits idle inside the cache pool, unable to satisfy future requests unless a tensor of that exact (or smaller) size is requested.
  • Bimodal Allocation Patterns: Deep learning training oscillates between allocating many small gradient buffers/activations and a few massive model weights/embeddings. As large blocks are freed, they leave “cracks” in the memory map that small blocks can’t fill efficiently, and vice-versa.
  • Alignment & Suballocator Limits: The suballocator splits raw CUDA memory into aligned chunks. When you repeatedly allocate and free tensors of different sizes, these chunks become misaligned or split by already-allocated tensors. PyTorch has no mechanism to compact or coalesce these scattered free blocks while the training loop is running.

3. Seeing it in Action

You can observe fragmentation via two metrics: * torch.cuda.memory_reserved(): The total memory requested from the CUDA driver (includes cache). * torch.cuda.memory_allocated(): The actual bytes currently holding live tensors.

The difference (reserved - allocated) is your fragmentation / cache overhead. If this gap grows steadily over time, your allocator is hoarding scattered blocks it can’t efficiently repack.

Quick Mitigations (if needed)

  • torch.cuda.empty_cache(): Forces the caching allocator to return all free memory to the system. Use sparingly; it will incur a performance hit on the next allocation because PyTorch has to request fresh memory from the driver.
  • Gradient Accumulation / Fixed Batch Sizes: Keeping tensor shapes more uniform reduces the variety of block sizes floating in the cache.
  • PYTORCH_CUDA_ALLOC_CONF: You can tune allocator behavior via environment variables, such as enabling a split-pool strategy or setting maximum cache sizes (e.g., PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.8,max_split_size_mb:128).
